# USDT 到账数据源改为币安 API

- 日期：2026-11-23
- 状态：待确认
- 关联：`docs/otok/USDT_PAYMENT.md`（现有链上监听的完整规则）

## 背景与目的

USDT 渠道的 4 个收款地址（BSC / Polygon / ERC20 共用 `0xbd7c…`，TRC20 为 `TWZS…`）都是站长自己的币安充值地址。付 BEP20、TRC20 的用户大多从币安提币。币安发现收款地址也属于币安用户时，会走内部的「链下转账」（`Off-chain transfer <编号>`）：不上链、0 手续费、几秒到账。现在的监听只看链上，永远看不到这类付款，只能由站长人工核对后加余额。截至 2026-11-23，BEP20 订单 24 单只自动成功 1 单，TRC20 10 单一单都没成功；最近 4 笔链下付款全部靠人工处理。

币安只读 API 的充值记录（`GET /sapi/v1/capital/deposit/hisrec`）同时包含链上充值和链下转账，判断的就是「钱是否真的进了账户」。这次把它作为 USDT 到账的**唯一数据源**：4 条链和链下转账走同一套逻辑。链上监听代码保留，作为可切回的备用数据源。

已实测：

- 链下转账在接口里是 `transferType=1`、`txId="Off-chain transfer 434226888519"`，`amount` 精确等于用户填的金额，`status=1`，`insertTime` 比对方转出晚约 8 秒。
- 链上充值从出块到币安记下（`insertTime`）：中位数 BSC 7 秒、Polygon 16 秒、ETH 21 秒。ETH、Polygon 的 `completeTime` 要几分钟到十几分钟，那是币安等「提现解锁」的确认数，此前钱已计入余额（`status=6`）。
- otok 服务器在美国，直连币安返回 451。经站长购买的东京代理（出口固定为 `14.137.229.97`，HTTP / SOCKS5）可正常访问。API key 只读，IP 白名单就是这个出口。

## 目标

1. 币安用户的链下转账自动匹配订单、自动入账，延迟和现在的链上入账相当（1 分钟内）。
2. 4 条链的链上付款改为以币安充值记录为准，不再依赖公共 RPC / TronGrid。
3. 数据源可以在后台一键切回链上节点，不用重新部署。
4. 币安或代理不可用时，后台能看到原因，并有 Telegram 告警。

## 非目标

- 不接币安 Pay（商户收款），不做退款。
- 不改金额规则（唯一尾差、汇率、手续费、预留和保留期）。
- 不同时运行两个数据源（方案 B 已否决）。
- 不支持 4 条链以外的网络（如 Plasma），这类充值继续人工处理。

## 反目标（技术上能跑通也算失败的情况）

- 同一笔付款入账两次，或者匹配到别人的订单。
- 钱还没真正到账（币安 `status` 为 0 / 2 / 7 / 8）就给用户加了余额。
- 用户随手提交一个编号，就能改动别人待匹配转账的状态（与现在用户提交 TxHash 的约束相同）。
- 代理或币安故障时悄无声息：订单只是一直「待支付」，没人知道原因。

## 约束

- fork 硬规则：不改 Ent schema；上游文件只放带 `// otok` 标记的钩子；迁移只能新增、必须幂等；不加 Go / npm 依赖。签名只用标准库 `crypto/hmac`。
- 币安接口：`hisrec` 每次请求权重 1，`limit` 最大 1000，`startTime` 到 `endTime` 不超过 90 天，`recvWindow` 最大 60000。`status` 取值：0 处理中、1 成功、2 拒绝、6 已入账但不能提现、7 充错、8 等待用户确认（travel rule）。
- 代理是第三方服务，账号密码只放服务器 `.env`（权限 600）。
- 生产有真实付费用户，上线前要做全库备份。

## 方案比较

| 方案 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| **A. 全部改走币安（采用）** | 链上充值和链下转账都只看币安充值记录；链上监听保留为可切回的备用 | 一个数据源，标准就是「钱进了账户」；不再受 RPC / TronGrid 故障影响 | 币安和代理成为单点；靠告警和一键切回兜底 |
| B. 币安为主，链上同时兜底 | 两个数据源同时跑 | 单个数据源故障时不中断 | 同一笔链上付款会被记两次（币安记录没有日志序号），两边不一致还要定规则，复杂度都在入账路径上；现在一天只有几单，不值得 |
| C. 链上照旧，币安只补链下 | 只把 `transferType=1` 的记录接进来 | 改动最小；代理故障只影响链下 | 长期维护两套机制，RPC 的老问题还在 |

站长选 A，理由：收款地址全是币安充值地址，「币安说到账了」是最准的判断标准；单点风险用告警和开关来兜。

## 设计

### 1. 配置

USDT 渠道实例（`payment_provider_instances`，`provider_key=otok_usdt`）新增 3 个配置项：

| key | 说明 |
| --- | --- |
| `depositSource` | `binance` / `chain`。**缺省为 `chain`**，旧配置升级后行为不变；站长填好 key 后在后台切到 `binance` |
| `binanceApiKey` | 敏感字段：列表不回显，审计脱敏 |
| `binanceApiSecret` | 同上 |

- `depositSource=binance` 时两个 key 必填，否则保存失败。
- 渠道配置在库里是明文 JSON（上游已去掉加密），所以 secret 会进全库备份。这把 key 只读，又限定了代理出口 IP，风险可接受。
- 环境变量：
  - `OTOK_USDT_BINANCE_PROXY`：代理 URL，含账号密码，支持 http / https / socks5，经 `httpclient.Options.ProxyURL` 生效。未设置时直连，生产环境会 451，报错会显示在后台健康状态里。
  - `OTOK_USDT_BINANCE_API_URL`：覆盖币安接口地址，只给测试用。
- 切到 `binance` 后，TronGrid key 和 RPC 地址仍然保留，只是不再使用，切回 `chain` 时直接生效。

### 2. 币安客户端（`internal/pkg/otokchain/binance.go`）

- 带签名的 GET：`timestamp` 加 `recvWindow=10000`，HMAC-SHA256 签名，请求头 `X-MBX-APIKEY`。
- 只提供两个方法：
  - `Deposits(ctx, startTime, endTime)`：调用 `coin=USDT&includeSource=true&limit=1000`，超过 1000 条用 `offset` 翻页，最多 3 页。
  - `DepositsByTxID(ctx, txId)`：按 `txId` 精确查询。
- 网络映射写死：`BSC→bep20`、`ETH→erc20`、`MATIC→polygon`、`TRX→trc20`，其他网络一律忽略。
- 金额字符串（如 `"7.52"`、`"9.935984"`）按该网络 USDT 精度换算成 `amount_raw`，沿用现有的分值判断。
- 错误信息不带 URL 和 query（避免签名、key 进日志）。不跟随重定向，响应体有大小上限，与现有 `doJSON` 一致。
- 币安返回的错误码原样带进错误信息，例如 `-2015` 表示 key 无效或 IP 不在白名单，方便后台直接看出原因。

### 3. 轮询与入库

- 仍是每 15 秒一轮、Redis 选主，没有活跃预留时不发请求，规则不变。`depositSource=binance` 时，用币安轮询替换链上扫描这一步（`scanAndMatch`），其余步骤（释放预留、匹配、入账）照旧。
- 查询窗口：`startTime` 为最早活跃预留的下单时间减 2 分钟，`endTime` 为当前时间。数据量很小，每轮整窗重拉，不维护游标；用游标表里 `network='binance'` 这一行记录最近成功 / 失败。
- 入库条件：`coin=USDT`，网络能映射，`address`（小写或 base58 原样比较）等于当前配置的某个收款地址，`status` 不是 2 或 7。
- 写进 `otok_usdt_transfers`，`source='binance'`：
  - `tx_hash`：链上充值用 `NormalizeTxHash` 后的哈希，和币安的 `txId` 形式一致，都是小写；链下转账原样存币安的 `txId`（`Off-chain transfer …`）。
  - `log_index`：-1。同一 `txId` 下有多笔充值时，按币安 `id` 排序依次用 -1、-2…，和链上记录（≥0）不会冲突。
  - `block_time`：`insertTime`。`from_address`：`sourceAddress`。`block_number`、`block_hash` 留空。
  - 新列 `external_id`：币安充值记录的 `id`，带唯一索引，重复轮询时按它幂等更新。
  - 币安的 `status`、`confirmTimes` 不入库，入账复核时再实时查询。

### 4. 匹配规则（与现在的差异）

仍是「地址 + 精确金额 + 时间窗 + 下单后首次记录」，区别有两点：

- **网络可以不一致**：币安来源的记录，只要地址相同就匹配，不要求网络一致。比如订单是 BEP20，用户选 Polygon 转到同一地址，钱同样进了同一个币安账户。同一地址的尾差金额本来就跨网络唯一，不会串单。`otokBoundTransferMismatch` 对币安来源同样放宽这一条。
- 时间窗用 `insertTime`。链上充值比出块晚 7～21 秒才被币安记下，保留期末尾只差几秒的情况可以忽略。

记录在 `status=0`（处理中）时就允许匹配和绑定，相当于链上「已上链、确认数不够」；入账要等复核通过。

### 5. 入账复核

`creditBoundTransfer` 里的 `verifyOnChain` 对币安来源的记录改走 `verifyOnBinance`，按 `txId` 查询，再按 `external_id` 找到这一条：

| 币安状态 | 处理 |
| --- | --- |
| 1 或 6 | 视为已确认，核对地址、金额、币种一致后入账（金额不一致的处理和现在相同：转待审核，管理员补单的除外） |
| 0 | 继续等，`last_error` 写「币安处理中（确认数 x/y）」 |
| 8，或 `travelRuleStatus=1` | 继续等，`last_error` 写「币安要求补充 travel rule 信息，请到币安 App 处理」，后台会显示为「入账受阻」 |
| 2 或 7 | 解绑并转待审核 |
| 查不到 | 按现有「链上消失」逻辑：15 分钟后解绑 |
| 接口出错 | 保持原状，下一轮重试，不计入重试次数（和 RPC 出错一样） |

**复核方式只看记录来源，不看当前开关**：`source='binance'` 的记录永远向币安复核，其他来源的记录永远上链复核。数据源开关只决定「从哪里发现新付款」，所以来回切换时，已绑定的记录都能按原来的方式走完入账。

### 6. 用户提交编号 / 管理员补单

- 币安模式下，付款页的输入框同时接受：
  - 链上交易哈希；
  - `Off-chain transfer 434226888519`、`链下转账 434226888519` 或纯数字编号。数字编号统一转成币安 `txId` 去查询。
- 用币安查到记录后，按第 3 节入库，再走现有校验（金额精确、时间窗、首次记录、转账未匹配）。不满足条件时只记审计日志 `OTOK_USDT_TX_REJECTED`，不改转账状态，和现在一样。
- 管理员补单同样支持这两种输入。币安状态必须为 1 或 6，允许金额不一致，需填原因。**已取消订单也能补**（用户等不及取消后才到账是最常见的情况），这样可以替代现在的手工加余额。
- 链上模式下行为不变，输入链下编号时提示「当前数据源不支持链下转账」。

### 7. 前端

- 渠道配置：`depositSource` 下拉（「币安 API（推荐）」/「链上节点」），`binanceApiKey`、`binanceApiSecret` 为敏感输入框，并附简短提示。中英文案同步。
- 付款面板：订单详情接口新增 `deposit_source` 字段。币安模式下：
  - 输入框占位改为「交易哈希或链下转账编号」；
  - 加一行提示：「从币安提币（包括显示『链下转账』的）都会自动到账，一般 1 分钟内」。
- 「USDT 到账记录」页：
  - 来源显示「币安」；链下转账显示编号，不显示区块浏览器链接，链上的仍然链接到浏览器；
  - 监听状态增加「币安 API」一行，显示最近成功时间和最近错误。

### 8. 告警

在 `balance-monitor` 加一种上游类型 `binance`：每 10 分钟经同一代理做一次签名请求，读取资金账户的 USDT 余额，一次就能验证代理、出口 IP 白名单和 key 三件事。

- 复用现有的「连续失败 3 轮告警、恢复后通知」。
- 阈值设为 0，即不做低余额告警。`/balance` 里会顺带显示收款账户余额。
- 配置里要再放一份代理和只读 key，写在 `config.json`（权限 600）。

sub2api 自身只在后台监听状态里显示错误，不另做推送。

### 9. 迁移

新增 `backend/migrations/otok_0005_usdt_binance.sql`，幂等：

```sql
ALTER TABLE otok_usdt_transfers ADD COLUMN IF NOT EXISTS external_id VARCHAR(64) NOT NULL DEFAULT '';
CREATE UNIQUE INDEX IF NOT EXISTS otok_usdt_transfers_external_uniq
    ON otok_usdt_transfers (source, external_id) WHERE external_id <> '';
```

转账表很小（几十行），不用预建索引。旧版本不读这一列，回滚不受影响。

### 10. 测试

- 单元测试：
  - 签名结果对照币安官方文档的示例；
  - 网络映射、金额换算、链下编号的各种输入写法；
  - 6 种 `status` 的复核分支；
  - 跨网络匹配；
  - 同一 `txId` 下多笔充值的序号分配；
  - 配置校验（binance 模式缺 key 报错，缺省为 chain）。
- 集成测试（testcontainers，`-run Otok`）：用 `httptest` 模拟币安，跑通「下单 → 链下转账 → 匹配 → 入账」；覆盖 `status=0` 等待、`status=8` 受阻、取消订单后由管理员补单、用户提交编号被拒且不改状态。
- 前端：配置字段渲染、付款面板在两种数据源下的提示，以及 i18n key 完整性。

### 11. 上线与回滚

1. 发版 `otok-v0.2.24.2`。
2. 全库备份。在 `.env` 加 `OTOK_USDT_BINANCE_PROXY`（备份 `.env`），换镜像并重建容器，核对 `--version`。此时数据源仍是 `chain`，行为不变。
3. 站长在后台填 key / secret，把 `depositSource` 切到 `binance`。到「USDT 到账记录」确认「币安 API」一行显示成功。
4. 实测：站长用另一个币安账号下一笔最小金额的订单，走链下转账，确认 1 分钟内自动到账。
5. 部署 balance-monitor 新版本，执行 `-once` 确认币安一项正常。
6. 更新 `USDT_PAYMENT.md`、上级 `CLAUDE.md`（定制功能表、运维要点、回滚说明）。

回滚：

- 后台把 `depositSource` 切回 `chain`，立即生效，链下转账回到人工处理。
- 或者把镜像换回 `0.2.24-otok.1`。`external_id` 列留在库里，不影响旧版本；已入库的币安来源记录在旧版本里会被当成链上记录去复核，查不到交易，只会停在原状态，不会误入账。如果要回滚镜像，先确认没有「已匹配未入账」的币安来源记录。

## 我拍板的决定（请过目）

1. 缺省数据源是 `chain`，上线后由站长在后台手动切换，不随升级自动切。
2. 币安来源的记录跨网络匹配（同地址即可）。
3. `status=6`（已入账、暂不能提现）就算到账，不等解锁。
4. API key / secret 放后台配置（库内明文，与 TronGrid key 相同），代理放 `.env`。
5. 管理员补单可以绑定已取消的订单（现有逻辑本来就允许，这里只是明确链下转账也适用）。
6. 告警放在 balance-monitor（走现有的 TG），sub2api 不新增推送渠道。

## 留给实现时决定

- 复核时是复用本轮的轮询结果，还是每笔单独按 `txId` 查询（量很小，两种都可以）。
- 链下编号目前只见过 `Off-chain transfer <编号>` 这一种前缀。按 `txId` 查不到时，再在订单时间窗内的充值记录里按「`txId` 以 ` <编号>` 结尾」兜底查找，防止币安换了前缀（例如 `Internal transfer`）。
- 后台各处文案的具体措辞。
- 代码在 `otok_usdt_watcher.go` 和新文件之间怎么拆分。
